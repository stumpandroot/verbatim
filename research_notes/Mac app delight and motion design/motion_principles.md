# Interface motion and micro-interaction principles (2023–2026)

Scope: rules of thumb and numbers for making a minimal utility app feel responsive and alive. Sources are primary where possible (Apple HIG and WWDC transcripts, Emil Kowalski, Josh Comeau, web.dev, published design-system token docs). Where a value comes from a secondary aggregator or from my own prior knowledge rather than a fetched page, it is flagged.

Fetch note: several pages (rauno.me, m3.material.io, the full Emil skill summary) could not be fetched in this session because the fetch tool required a permission that was not granted in time. Those are listed under Gaps rather than reconstructed from memory.

## Key question 1: What concrete numbers do experts recommend (durations, springs, staggers), and from whom?

### Takeaway
There is strong convergence: feedback and most UI transitions should land under ~300 ms (Emil Kowalski says "usually shorter than 300ms"; web.dev gives 200–500 ms for ease-out/ease-in; production design systems put hover/press at 100–150 ms, standard transitions at 200 ms, large surfaces at 300–480 ms). Apple's spring model replaces duration+curve with duration+bounce, with bounce 0 as the versatile default, ~0.15 barely bouncy, ~0.3 noticeably bouncy, and >0.4 flagged as too exaggerated for UI. Stagger examples run ~100 ms per item with the first item starting at 0 ms.

### Cited Findings

Durations
- "Your animations should also usually be shorter than 300ms." Fast animations improve perceived performance; a spinner that looks like it is working harder feels faster even when load time is identical. — [Emil Kowalski, Great Animations](https://emilkowal.ski/ui/great-animations)
- Animations must run at 60 fps or the other principles lose value. — [Emil Kowalski, Great Animations](https://emilkowal.ski/ui/great-animations)
- Emil's own reduced-motion CSS example uses a 0.2 s (200 ms) bounce animation by default and swaps to a 0.2 s fade under `prefers-reduced-motion: reduce`. — [Emil Kowalski, Great Animations](https://emilkowal.ski/ui/great-animations)
- A 500 ms enter animation in a keyboard-driven tool like Raycast "would feel slow and disconnected"; never animate keyboard-initiated actions that repeat many times a day. — [Emil Kowalski, Great Animations](https://emilkowal.ski/ui/great-animations)
- Ease-out: about 200–500 ms, the default choice for UI ("generally speaking, an ease-out will be the right call"); for a snappier feel use a quintic ease-out. Ease-in: about 200–500 ms, but ease-ins "jolt at the end." Bounce/elastic easings: about 800–1200 ms so the effect has time to settle, used sparingly and only when they fit the project's personality. Too short feels aggressive; too long feels obstructive. — [web.dev, Choosing the right easing](https://web.dev/articles/choosing-the-right-easing)
- Reshaped design-system tokens: rapid 100 ms (button press states, menu items responding to pointer), fast 150 ms (default for hover/focus/color changes), medium 200 ms (overlay backdrop, toast, progress bar), slow 300 ms (long-distance travel such as an animated tabs indicator). — [Reshaped, Animation tokens](https://reshaped.so/docs/tokens/animation)
- Polar "Orbit" design-system tokens: instant 0 ms, fast 120 ms (hover, focus, small toggles), base 200 ms (default), slow 320 ms (larger surfaces entering/leaving), slower 480 ms (full-screen or emphasis moments). Recommended pairing for elements entering toward the pointer: fast (120 ms) + decelerate. — [Polar Orbit, Motion](https://orbit.polar.sh/foundations/motion)
- Another published token set: instant 50 ms (focus rings, micro-feedback), fast 100 ms (hover, border color, input focus), normal 200 ms (buttons, tabs, accordions), slow 400 ms (structural movement, progress bars), deliberate 700 ms (large orchestrated shifts). — [davaux UI docs, Motion](https://davaux.codeberg.page/ui-docs/motion)
- Apple HIG: for games, "maintaining a consistent frame rate of 30 to 60 fps typically results in a smooth, visually appealing experience." — [Apple HIG, Motion (JSON)](https://developer.apple.com/tutorials/data/design/human-interface-guidelines/motion.json)

Easing curves (cubic-bezier values)
- Standard `cubic-bezier(0.2, 0, 0, 1)` for elements moving within the layout while staying on screen; accelerate `cubic-bezier(0.4, 0, 1, 1)` for elements leaving (modal, flyout, overlay, toast on close); decelerate `cubic-bezier(0, 0, 0.2, 1)` for elements entering (overlay, modal, flyout, toast on open). — [Reshaped, Animation tokens](https://reshaped.so/docs/tokens/animation)
- Standard `cubic-bezier(0.2, 0, 0, 1)` (general-purpose default), decelerate `cubic-bezier(0, 0, 0, 1)` (enter: moves quickly then settles), accelerate `cubic-bezier(0.3, 0, 1, 1)` (exit: starts settled then moves quickly), "spring" `cubic-bezier(0.5, 1.25, 0.4, 1)` (slight overshoot for playful emphasis). — [Polar Orbit, Motion](https://orbit.polar.sh/foundations/motion)
- Standard `cubic-bezier(0.4, 0, 0.2, 1)`, enter `cubic-bezier(0, 0, 0.2, 1)`, exit `cubic-bezier(0.4, 0, 1, 1)`, plus a CSS `linear()` spring curve for modals and drawers that overshoots and settles without JavaScript. — [davaux UI docs, Motion](https://davaux.codeberg.page/ui-docs/motion)
- Built-in CSS curves are "usually not strong enough"; custom curves feel more energetic. `ease` is acceptable only for basic hover effects like background color changes. Default to `ease-out` in most cases; use `ease-in-out` when moving an element that is already on screen. — [Emil Kowalski, Good vs Great Animations](https://emilkowal.ski/ui/good-vs-great-animations)
- `ease-out` for responsiveness (starts fast, slows at the end). Emil's Sonner toast library deliberately uses `ease` and a slower-than-usual duration to feel more elegant (exact duration not stated). — [Emil Kowalski, Great Animations](https://emilkowal.ski/ui/great-animations)

Springs (Apple model)
- Springs are the default SwiftUI animation; `withAnimation { }` runs a spring. Two parameters: duration and bounce. If you do not specify bounce, it defaults to 0, "a great general purpose spring that's the most versatile." — [WWDC23 Animate with springs, transcript](https://developer.apple.com/videos/play/wwdc2023/10158/)
- Bounce ranges: 0 = smooth, gradual change; ~0.15 (15%) "doesn't feel very bouncy yet, but the long tail feels a little more brisk"; ~0.3 (30%) "you do start to feel some noticeable bounciness"; "be cautious about using values higher than around 0.4, since they may feel too exaggerated for a UI element." API range is -1.0 to 1.0 (negative = flattened/overdamped). — [WWDC23 Animate with springs, transcript](https://developer.apple.com/videos/play/wwdc2023/10158/)
- Add bounce "if you want your animation to feel a little more playful" or "when you want an animation to feel more physical, like if it's going to be used at the end of a gesture." Choose consistently based on app character: serious or playful, relaxed or fast-paced. — [WWDC23 Animate with springs, transcript](https://developer.apple.com/videos/play/wwdc2023/10158/)
- Duration is a perceptual duration "chosen to be predictable and not move around, even as the other parameters of a spring change." Settling duration is unpredictable; "you shouldn't wait for the settling duration for user-facing changes." SwiftUI's completion handler fires on perceptual duration. — [WWDC23 Animate with springs, transcript](https://developer.apple.com/videos/play/wwdc2023/10158/)
- Presets `.smooth`, `.snappy`, `.bouncy` exist and can be tuned: `.snappy(duration: 0.4)`, `.snappy(extraBounce: 0.1)`; custom: `.spring(duration: 0.6, bounce: 0.2)`, `UIView.animate(duration: 0.6, bounce: 0.2)`, `CASpringAnimation(perceptualDuration: 0.6, bounce: 0.2)`. — [WWDC Notes, Animate with springs](https://wwdcnotes.com/documentation/wwdc23-10158-animate-with-springs/)
- Conversion from (duration, bounce) to physical parameters, as rendered in the session: mass = 1; stiffness = (2π / duration)²; damping = 1 − 4π·bounce / duration for bounce ≥ 0, and 4π / (duration + 4π·bounce) for bounce < 0. — [WWDC23 Animate with springs, transcript](https://developer.apple.com/videos/play/wwdc2023/10158/) (Note: the fetched transcript rendering of the damping formula looks dimensionally odd; verify against Apple's `Spring` documentation before relying on it.)
- UIKit/AppKit in 2024: `UIView.animate(springDuration: 0.5)` is a 0.5 s spring; `UIView.animate(.spring(duration: 0.5))` accepts a SwiftUI animation. For gestures, use `.interactiveSpring` during `.changed` and `.spring` on `.ended`; SwiftUI handles velocity. — [WWDC Notes, Enhance your UI animations and transitions (WWDC24 10145)](https://wwdcnotes.com/documentation/wwdc24-10145-enhance-your-ui-animations-and-transitions/)

Springs (web, Josh Comeau)
- Spring parameters: mass (heavier moves more slowly but has more inertia), tension/stiffness (higher = snappier, bouncier), friction/damping (more = less bouncy; without it springs oscillate forever). Josh's sandbox defaults: mass 1.75, tension 200, friction 12. — [Josh Comeau, A Friendly Introduction to Spring Physics](https://joshwcomeau.com/animation/a-friendly-introduction-to-spring-physics/)
- Use springs mainly for motion; Josh "wouldn't use them for color or opacity changes." — [Josh Comeau, A Friendly Introduction to Spring Physics](https://joshwcomeau.com/animation/a-friendly-introduction-to-spring-physics/)

Material 3 Expressive springs (partial)
- Material Expressive default spatial spring: stiffness 380, damping ratio 0.73 (from the Flutter `material_expressive` package implementing M3 Expressive's MotionScheme; other tiers listed without values). — [material_expressive 0.8.0 docs](https://pub.dev/documentation/material_expressive/0.8.0/)

Staggers
- Example stagger: 100 ms per item (0, 100, 200, 300, 400 ms for five items), each item animating over 400 ms; the first item must start with no delay because "a delay in the initiation of the effect can make a user think that something went wrong." Items overlap when delay < duration (e.g., 100 ms delay with 300 ms duration); delay equal to duration feels "more mechanical." — [LogRocket, CSS staggered animations](https://blog.logrocket.com/css-staggered-animations/)

### Inferences
- A practical macOS default set that fits all cited sources: hover/press 100–150 ms ease-out; state changes and small reveals 200 ms; panel/sheet entrance 250–320 ms decelerate; exits 20–40% shorter with accelerate; springs at duration 0.3–0.5 s with bounce 0–0.15 for utility UI, 0.2–0.3 only for playful moments.
- Several design systems (Reshaped, Polar) use the same standard curve `cubic-bezier(0.2, 0, 0, 1)` and the same enter/exit split; this is the Material 3 "standard" family. The `(0.4, 0, 0.2, 1)` curve is the older Material 2 standard. I did not fetch m3.material.io directly, so treat the attribution as inference.
- Stagger totals should be capped: at 100 ms per item, anything over ~6 items pushes the last entrance past 500 ms, which conflicts with the "under 300 ms" feel. Use 30–60 ms steps for longer lists (inference, not cited).

## Key question 2: How do Apple's guidelines (HIG Motion, WWDC23/24/25) define good motion on macOS?

### Takeaway
Apple's HIG is short on numbers and long on restraint: add motion purposefully, keep feedback brief and precise, avoid animating frequent interactions, let people cancel motion, and make motion optional. The platform-specific macOS section says "no additional considerations." WWDC23 establishes springs as the default because they preserve velocity through gestures and interruptions; WWDC24 adds interruptible zoom transitions; WWDC25's Liquid Glass responds with "greater emphasis" to touch and a "more subdued effect" for trackpad input, and Reduce Motion disables the material's elastic properties.

### Cited Findings
- "Add motion purposefully, supporting the experience without overshadowing it. Don't add motion for the sake of adding motion. Gratuitous or excessive animation can distract people and may make them feel disconnected or physically uncomfortable." — [Apple HIG, Motion](https://developer.apple.com/tutorials/data/design/human-interface-guidelines/motion.json)
- "Make motion optional." Never use motion as the only way to communicate important information; supplement with haptics and audio. — [Apple HIG, Motion](https://developer.apple.com/tutorials/data/design/human-interface-guidelines/motion.json)
- "Strive for realistic feedback motion that follows people's gestures and expectations." Example: a view revealed by sliding down from the top should not be dismissed by sliding sideways. — [Apple HIG, Motion](https://developer.apple.com/tutorials/data/design/human-interface-guidelines/motion.json)
- "Aim for brevity and precision in feedback animations." Brief, precise feedback "tends to feel lightweight and unobtrusive, and it can often convey information more effectively than prominent animation." — [Apple HIG, Motion](https://developer.apple.com/tutorials/data/design/human-interface-guidelines/motion.json)
- "In apps, generally avoid adding motion to UI interactions that occur frequently." The system already animates standard elements subtly; for custom elements, avoid making people spend extra time on unnecessary motion every time they interact. — [Apple HIG, Motion](https://developer.apple.com/tutorials/data/design/human-interface-guidelines/motion.json)
- "Let people cancel motion. As much as possible, don't make people wait for an animation to complete before they can do anything, especially if they have to experience the animation more than once." — [Apple HIG, Motion](https://developer.apple.com/tutorials/data/design/human-interface-guidelines/motion.json)
- "Consider using animated symbols where it makes sense" (SF Symbols 5 or later). — [Apple HIG, Motion](https://developer.apple.com/tutorials/data/design/human-interface-guidelines/motion.json)
- Platform considerations for iOS, iPadOS, macOS, tvOS: "No additional considerations." The HIG Motion page contains no reduce-motion section and no numeric durations. — [Apple HIG, Motion](https://developer.apple.com/tutorials/data/design/human-interface-guidelines/motion.json)
- Liquid Glass guidance added September 9, 2025: "the movement of Liquid Glass responds to direct touch interaction with greater emphasis to reinforce the feeling of a tactile experience, but produces a more subdued effect when a person interacts using a trackpad." — [Apple HIG, Motion](https://developer.apple.com/tutorials/data/design/human-interface-guidelines/motion.json)
- visionOS-only but useful as a physiological limit: avoid sustained oscillation around 0.2 Hz, "because people can be very sensitive to this frequency"; keep amplitude low. — [Apple HIG, Motion](https://developer.apple.com/tutorials/data/design/human-interface-guidelines/motion.json)
- Why springs: "springs are the only type of animation that maintains continuity both for static cases and cases with an initial velocity." Ease-in-out "jerks to a halt as the gesture ends" because it cannot take an initial velocity. On retargeting, "a spring animation uses the velocity it had when it was retargeted as the initial velocity towards its new destination," making interruptions "feel smooth and natural." — [WWDC23 Animate with springs](https://developer.apple.com/videos/play/wwdc2023/10158/)
- Linear curves have "a sharp corner and a jump in velocity"; useful "as a specialized tool in some places, like a repeating spinning indicator, but otherwise you should be cautious about using them, especially for movement." — [WWDC23 Animate with springs](https://developer.apple.com/videos/play/wwdc2023/10158/)
- A spring "very slowly and gradually comes to rest," and different properties finishing at different times is intended. — [WWDC23 Animate with springs](https://developer.apple.com/videos/play/wwdc2023/10158/)
- WWDC24: zoom transitions (`.matchedTransitionSource` + `.navigationTransitionStyle(.zoom)`) are "continuously interactive," so users can interrupt and redirect them; "be ready for a transition to start at any time, and don't treat 'in transition' as a special state"; keep temporary transition state minimal and reset it in `viewDidAppear`/`viewDidDisappear`. — [WWDC Notes, WWDC24 10145](https://wwdcnotes.com/documentation/wwdc24-10145-enhance-your-ui-animations-and-transitions/)
- WWDC25 "Meet Liquid Glass" (session 219): glass responds to touch by "instantly flexing and energizing with light"; menus "pop open from the tapped control" as a bubble, keeping a clear link to the button; glass objects appear and disappear by changing how light lenses through them rather than fading; when a window loses focus on Mac or iPad, the glass visually recedes; "Reduced Motion decreases the intensity of some effects and disables the material's elastic properties." No numeric motion values are given. — [Meet Liquid Glass transcript (nonstrict index)](https://nonstrict.eu/wwdcindex/wwdc2025/219/)

### Inferences
- For a pointer-driven Mac utility, Apple's own 2025 direction is "subdued" compared with touch: flex and glow are muted for trackpad input, so a Mac app should keep hover/press feedback small (opacity/brightness shifts, 1–2% scale) rather than touch-style squash.
- Apple's "avoid motion on frequent interactions" plus Emil's "never animate keyboard-initiated actions" together argue that a utility app's core loop (paste link, transcribe, search) should have near-zero motion, with motion reserved for state changes (processing to done), appearances (sheets, popovers), and errors.

- Could not fetch the WWDC24 "Design with SwiftUI"/"Enhance your UI animations" official transcript directly; findings rely on WWDC Notes summaries.
- No 2025 WWDC session specifically about motion values for Liquid Glass was found; "Meet Liquid Glass" is descriptive only.

## Key question 3: What do Emil Kowalski, Rauno Freiberg, Josh Comeau, Jenny Wen, and Disney-principle UI writers say that is directly usable?

### Takeaway
Emil's rules are the most operational: under 300 ms, ease-out by default, custom curves over built-ins, transform-origin at the trigger, animate only `transform`/`opacity`, interruptible CSS transitions over keyframes, never animate frequent or keyboard actions, and "no animation" is sometimes the right answer. Josh Comeau supplies the spring mental model. The Disney principles map cleanly onto UI (squash and stretch as press feedback, anticipation as hover preview, follow-through as staggered secondary elements, timing as enter-slower/exit-faster). Rauno and Jenny Wen could not be sourced on motion in this session.

### Cited Findings

Emil Kowalski
- Set `transform-origin` to where the trigger sits (a dropdown opened by a button uses `bottom center`; with Radix, `var(--radix-popover-content-transform-origin)`). — [Emil Kowalski, Good vs Great Animations](https://emilkowal.ski/ui/good-vs-great-animations)
- Spring-style motion suits decorative effects only; for a functional element like a banking graph, "no animation would be better." — [Emil Kowalski, Good vs Great Animations](https://emilkowal.ski/ui/good-vs-great-animations)
- For mouse-driven decorative effects, use `useSpring` (Framer Motion/Motion) so values interpolate instead of jumping. For tabs, animate with `clip-path` so the color transition blends with the moving highlight. Check timing frame by frame or in slow motion. — [Emil Kowalski, Good vs Great Animations](https://emilkowal.ski/ui/good-vs-great-animations)
- Animate `transform` and `opacity` only; padding/margin trigger layout + paint + composite. When the main thread is busy, hardware-accelerated CSS/WAAPI animations stay smooth; Framer Motion's `requestAnimationFrame` loop can lag (Vercel's dashboard tab animation dropped frames until moved to CSS). — [Emil Kowalski, Great Animations](https://emilkowal.ski/ui/great-animations)
- Interruptibility: "Users should be able to change an animation's state at any time and still get a smooth transition." CSS transitions can be interrupted and redirected; keyframe animations cannot as easily. — [Emil Kowalski, Great Animations](https://emilkowal.ski/ui/great-animations)
- Purpose and frequency: do not add animations everywhere; animate to explain, indicate state change, or handle enter/exit of elements like modals; consider how often users will see it. — [Emil Kowalski, Great Animations](https://emilkowal.ski/ui/great-animations)
- Reduced motion: use `prefers-reduced-motion` in CSS or `useReducedMotion` in Framer Motion; a reduced version can keep subtle opacity changes instead of movement; sidebar example uses closed position `-100%` on x, or `0` when reduced motion is preferred. — [Emil Kowalski, Great Animations](https://emilkowal.ski/ui/great-animations)
- Cohesion: easing, duration, and style should match the product's personality; finding good values "takes trial and error"; review animations the next day with fresh eyes. — [Emil Kowalski, Great Animations](https://emilkowal.ski/ui/great-animations)
- A community skill summarizing Emil's teaching lists "43 rules across 7 categories" drawn from his articles, Sonner, Vaul, and his animations.dev course; the rules themselves were truncated on the page. — [skills.sh, emilkowal-animations](https://skills.sh/mrmps/smry/emilkowal-animations)

Josh Comeau
- Springs produce "fluid and organic," "believable" motion; a spring-driven ball "slows to a stop in a way that CSS transitions can't replicate." Cubic Bézier curves have only two control points so they can only approximate springs; CSS `linear()` (2023) gets closer but is still not a true spring. Safari has a native CSS spring; other browsers do not. — [Josh Comeau, A Friendly Introduction to Spring Physics](https://joshwcomeau.com/animation/a-friendly-introduction-to-spring-physics/)
- Springs are JavaScript-only on the web; JS animations are as performant as CSS but can stutter on a busy main thread. — [Josh Comeau, A Friendly Introduction to Spring Physics](https://joshwcomeau.com/animation/a-friendly-introduction-to-spring-physics/)

Disney's 12 principles applied to UI (Arjun Kumar, UX Collective, Apr 3, 2024)
- Squash and stretch: slight elasticity for tactile feedback, such as buttons that compress on click; a card example expands with a subtle bounce. — [UX Collective, Disney's 12 principles exemplified in UX design](https://uxdesign.cc/disneys-12-principles-of-animation-exemplified-in-ux-design-5cc7e3dc3f75)
- Anticipation: a hover change that previews a dropdown; a carousel's partially visible next item. — [UX Collective](https://uxdesign.cc/disneys-12-principles-of-animation-exemplified-in-ux-design-5cc7e3dc3f75)
- Staging: choreograph entrances so one focal element stands out; avoid simultaneous animations competing for attention; skeleton loaders as placeholders. — [UX Collective](https://uxdesign.cc/disneys-12-principles-of-animation-exemplified-in-ux-design-5cc7e3dc3f75)
- Follow-through and overlapping action: drawer menu items start slightly after the drawer and settle after it stops; staggered list entrances; a button's icon moving at a different speed than the button. — [UX Collective](https://uxdesign.cc/disneys-12-principles-of-animation-exemplified-in-ux-design-5cc7e3dc3f75)
- Slow in/slow out: ease menus, modals, expanding content, and scroll instead of constant speed. — [UX Collective](https://uxdesign.cc/disneys-12-principles-of-animation-exemplified-in-ux-design-5cc7e3dc3f75)
- Arcs: move dragged or swiped elements along slightly curved paths. — [UX Collective](https://uxdesign.cc/disneys-12-principles-of-animation-exemplified-in-ux-design-5cc7e3dc3f75)
- Secondary action: an icon that rotates or bounces on tap; a spinning refresh icon; ripples on a confirmation checkmark. — [UX Collective](https://uxdesign.cc/disneys-12-principles-of-animation-exemplified-in-ux-design-5cc7e3dc3f75)
- Timing: "enter transitions can run longer so users can take in content, while exit transitions should be quicker so they don't pull focus from what's next." — [UX Collective](https://uxdesign.cc/disneys-12-principles-of-animation-exemplified-in-ux-design-5cc7e3dc3f75)
- Exaggeration: confetti or oversized badges for milestones; a text field that shakes near its character limit. — [UX Collective](https://uxdesign.cc/disneys-12-principles-of-animation-exemplified-in-ux-design-5cc7e3dc3f75)

Jenny Wen (Anthropic; previously led FigJam and Figma Slides)
- "The true value of a designer now lies in their obsessive dedication to craft and the subtle details that elevate a product." Polish differentiates products when basic functionality is easy to build. FigJam's playfulness was deliberate, to lower the barrier to entry. Great design requires "a visceral sense of how the product feels to use." No motion-specific statements were found. — [Antoine Buteau, Lessons from Jenny Wen](https://www.antoinebuteau.com/lessons-from-jenny-wen.md)

### Inferences
- Combining Emil's "default to ease-out" with the design-system enter/exit split: enter = decelerate (ease-out) at the longer duration; exit = accelerate (ease-in) at a shorter duration; on-screen moves = standard/ease-in-out. This matches the Disney "timing" rule (exit faster than enter).
- Press feedback for a Mac utility: squash via `scale(0.97–0.98)` over ~100 ms ease-out, release with a spring (bounce ~0.15) is consistent with Apple's bounce guidance and the 100 ms "rapid" tokens; the specific scale numbers are my inference, not cited.

## Key question 4: How should a mascot/character animate in a utility app (idle, reactions, blink rate, breathing, eye tracking)?

### Takeaway
Published mascot guidance is mostly structural (Rive state machines with idle, thinking, speaking, correct/incorrect reaction states, with blink, breathe, and talk layered concurrently) rather than numeric. The one cited interval is a game-dev convention of blinking every 5–10 s at random. Apple's HIG rules (avoid motion on frequent interactions, let people cancel motion, keep amplitude low for sustained oscillation) are the governing constraints for a mascot that lives on screen all day.

### Cited Findings
- Duolingo-style Rive mascot rig: idle includes breathing, blinking, and "subtle motion"; controllers listed include a blink controller, breathing motion control, and a pupil-tracking controller. State machine inputs: `isSpeaking` (bool), `mouthShape` (number), `isThinking`, `isCorrect`, `isWrong`. Thinking uses eye darts, head tilts, and eyebrow motion. Multiple behaviors run together ("blink + talk + breathe"). Reactions: correct, incorrect, encouragement. No loop lengths, blink frequencies, or amplitudes given. — [dev.to, Building a Duolingo-style interactive mascot in Rive](https://dev.to/uianimation/building-a-duolingo-style-interactive-mascot-in-rive-step-by-step-guide-2d5c)
- Lip sync: "Duolingo uses around 15–20 shapes, but 10+ works well for most apps"; starter viseme set A, E, O, M (closed), F/V, L, CH/J, Neutral, Smile, Surprise. — [dev.to, Building a Duolingo-style interactive mascot in Rive](https://dev.to/uianimation/building-a-duolingo-style-interactive-mascot-in-rive-step-by-step-guide-2d5c)
- Randomized idle blink in Adventure Game Studio: working version uses `Random(5)+5`, annotated "5-10 seconds," so each blink is scheduled 5–10 s after the previous one; a secondary idle (foot-tap) was proposed at roughly every fourth blink, and blink and body idles alternate rather than overlap. — [AGS forums, Randomized idle blinking](https://www.adventuregamestudio.co.uk/forums/beginners-technical-questions/solved-randomized-idle-blinking)
- Apple HIG: avoid motion on frequent interactions, let people cancel motion, and (visionOS) avoid sustained oscillation near 0.2 Hz, keeping amplitude low and content translucent if oscillation is needed. — [Apple HIG, Motion](https://developer.apple.com/tutorials/data/design/human-interface-guidelines/motion.json)
- Apple: add bounce when "you want your animation to feel a little more playful"; above ~0.4 is "too exaggerated for a UI element." — [WWDC23 Animate with springs](https://developer.apple.com/videos/play/wwdc2023/10158/)
- Staging principle: avoid simultaneous animations that compete for attention; one focal element at a time. — [UX Collective](https://uxdesign.cc/disneys-12-principles-of-animation-exemplified-in-ux-design-5cc7e3dc3f75)

### Inferences
- Idle loop structure that follows the sources: a slow breathing cycle (amplitude a few percent of character height; period several seconds, kept well away from a 0.2 Hz / 5 s sustained oscillation if the character is large), random blinks every 5–10 s with occasional double blinks, and a rarer secondary idle (look around, stretch) every ~4 blinks. Breathing amplitude and period numbers here are inference, not cited.
- Reactions should be event-driven (job started, job finished, error) and brief (under 300 ms to settle per Emil/Apple), with bounce 0.2–0.3 reserved for success moments.
- Pointer eye-tracking should be spring-smoothed (Emil's `useSpring` pattern for mouse-driven decorative effects) and should stop when the pointer leaves the window or when Reduce Motion is on; pupil travel should be a small fraction of eye radius to avoid reading as "watching."
- Provide a "quiet" mode: Apple's "make motion optional" and "let people cancel motion" imply the mascot should be hideable and should freeze (static pose, blink only or nothing) under Reduce Motion.

### Gaps
- No primary Duolingo, Headspace, Finch, Lookaway, or Apple Memoji/Clips source with numeric idle, blink, breathing, or eye-tracking values was found. The Duolingo blog post on world-character visemes appeared in search but was not fetched.
- No research-grade source on human blink rate was fetched (commonly cited as roughly 15–20 blinks per minute at rest, i.e., every 3–4 s; unverified here). The 5–10 s game convention is slower than physiological rate, which is typical for stylized characters to avoid distraction, but that reasoning is inference.
- No source quantified how often a mascot should "react" per session or the cost of reaction frequency on annoyance.

## Key question 5: Directional navigation, entrance/exit, hover/press, interruptibility, reduced motion, and the limits ("when motion becomes noise")

### Takeaway
Direction should be reversible and spatially consistent (Apple: a view that slides down from the top should not dismiss sideways). Enter with decelerate at the longer duration, exit with accelerate at the shorter one, originate transforms at the trigger, and make every transition interruptible and redirectable. Reduced motion should swap movement for opacity, not remove feedback. Motion becomes noise when it is frequent, keyboard-driven, functional-data-related, uncancellable, or purely ornamental.

### Cited Findings
- Spatial consistency: "if someone reveals a view by sliding it down from the top, they don't expect to dismiss the view by sliding it to the side." — [Apple HIG, Motion](https://developer.apple.com/tutorials/data/design/human-interface-guidelines/motion.json)
- Liquid Glass menus "pop open from the tapped control" keeping a clear link to the button; morphs preserve "one floating plane" between contexts. — [Meet Liquid Glass transcript](https://nonstrict.eu/wwdcindex/wwdc2025/219/)
- Enter = decelerate, exit = accelerate, in-place moves = standard, in two independent design systems (Reshaped: `(0,0,0.2,1)` / `(0.4,0,1,1)` / `(0.2,0,0,1)`; Polar: `(0,0,0,1)` / `(0.3,0,1,1)` / `(0.2,0,0,1)`). — [Reshaped](https://reshaped.so/docs/tokens/animation); [Polar Orbit](https://orbit.polar.sh/foundations/motion)
- Transform origin at the trigger for popovers/dropdowns. — [Emil Kowalski, Good vs Great Animations](https://emilkowal.ski/ui/good-vs-great-animations)
- Hover feedback: `ease` is fine for basic hover effects like background-color changes; hover/focus durations in design systems run 100–150 ms (Reshaped fast 150 ms; Polar fast 120 ms; davaux fast 100 ms). — [Emil Kowalski, Good vs Great Animations](https://emilkowal.ski/ui/good-vs-great-animations); [Reshaped](https://reshaped.so/docs/tokens/animation); [Polar Orbit](https://orbit.polar.sh/foundations/motion); [davaux](https://davaux.codeberg.page/ui-docs/motion)
- Press feedback: "rapid" 100 ms for button press states. — [Reshaped](https://reshaped.so/docs/tokens/animation)
- Interruptibility: users should be able to change state mid-animation with a smooth result (Emil); springs carry velocity across retargets (Apple WWDC23); WWDC24 transitions must be startable at any time and not treated as a special state. — [Emil Kowalski, Great Animations](https://emilkowal.ski/ui/great-animations); [WWDC23](https://developer.apple.com/videos/play/wwdc2023/10158/); [WWDC Notes WWDC24 10145](https://wwdcnotes.com/documentation/wwdc24-10145-enhance-your-ui-animations-and-transitions/)
- Reduced motion: replace movement with opacity (Emil's bounce-to-fade swap at 0.2 s; sidebar closed offset `-100%` to `0`); "reduced motion doesn't always mean remove motion" (LogRocket); Liquid Glass under Reduce Motion lowers effect intensity and disables elasticity (Apple). — [Emil Kowalski, Great Animations](https://emilkowal.ski/ui/great-animations); [LogRocket](https://blog.logrocket.com/css-staggered-animations/); [Meet Liquid Glass transcript](https://nonstrict.eu/wwdcindex/wwdc2025/219/)
- When motion becomes noise: gratuitous animation "can distract people and may make them feel disconnected or physically uncomfortable" (Apple); avoid motion on frequent interactions (Apple); never animate keyboard-initiated actions (Emil); overuse "overwhelms users and reduces their impact" (Emil); functional data should sometimes have no animation at all (Emil); bounce/elastic only when the personality warrants it, and jarring animation "pulls users out of an experience" (web.dev). — [Apple HIG](https://developer.apple.com/tutorials/data/design/human-interface-guidelines/motion.json); [Emil Kowalski, Great Animations](https://emilkowal.ski/ui/great-animations); [Emil Kowalski, Good vs Great](https://emilkowal.ski/ui/good-vs-great-animations); [web.dev](https://web.dev/articles/choosing-the-right-easing)

### Inferences
- Directional navigation for a Mac utility (push/pop or up/down): slide the incoming view in from the direction of travel with decelerate ~250–300 ms, slide the outgoing view partially (e.g., 20–30%) with a fade; pop reverses exactly, slightly faster. These offsets are inference; the reversal rule is Apple's.
- A simple audit rule drawn from the sources: for each animation ask (1) does it explain a state change or spatial relationship? (2) will it be seen more than a few times a session? (3) can the user interrupt it? (4) does it have an opacity-only reduced-motion variant? If (1) is no or (2) is yes without (3), cut it.

### Gaps
- No source gave numeric offsets (px or %) for directional push/pop slides on macOS; Apple's NavigationStack behavior is system-provided and not documented numerically.
- No cited hover scale values; design-system tokens cover duration but not scale. Values like `scale(1.02)` hover and `scale(0.97)` press are common practice but uncited here.
